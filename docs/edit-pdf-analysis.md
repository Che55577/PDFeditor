# 「編輯 PDF」該不該做？

結論先講：**不要當成一個功能做，要拆成三段，而且第三段可以不做。**

> **v0.1 基準 更新：階段一已完成，階段三的兩個前提都做了實測，結論有變動。**
> 直接看第八節之後。原本擋在階段三前面的「算圖效能」與「從零寫編輯器」兩個問題，
> 現在都有明確答案了。

## 一、先釐清 iLovePDF 的「Edit PDF」到底是什麼

它是**疊加註記層**，不是真正的內容編輯。使用者可以加文字方塊、圖片、形狀、手繪，
但**改不了文件裡既有的文字**。

這個區分是整份分析的關鍵，因為兩者的難度差了一個數量級：

| | 難度 | 說明 |
|---|---|---|
| 疊加層 | 中等 | 在原內容上面畫新東西，原內容完全不動 |
| 真編輯 | 極難 | 修改既有文字並重新排版 |

使用者看到「編輯 PDF」通常期待的是後者，實際拿到的是前者。**這個落差本身就是產品風險**——
如果我們做了疊加層卻叫它「編輯」，會收到跟 iLovePDF 一樣的抱怨。

## 二、真編輯為什麼是極難，而不只是工程量大

PDF 裡沒有「段落」這種東西。內容串流長這樣：

```
BT /F1 12 Tf 72 720 Td [(H) 3 (e) -2 (llo)] TJ ET
```

每個文字片段帶著絕對座標和字距微調陣列。要把 `Hello` 改成 `Hi`：

1. 先找出這串屬於視覺上哪一個「詞」——但檔案裡根本沒有詞的邊界資訊
2. 重新量測寬度（要讀字型的 hmtx 表）
3. 同一行後面的所有文字重新定位
4. 若變長超出行寬要重新斷行——但 PDF 不知道行寬，也不知道欄位邊界在哪
5. 兩端對齊的段落，字距是排版時預先算死的，整段都要重算

**問題不在工程量，在於資訊在產生 PDF 的那一刻就已經遺失了。** Adobe Acrobat 做這件事也
經常跑版。任何宣稱能完美做到的工具，實際上都是在猜。

## 三、疊加層的工作分解

| 項目 | 難度 | 現況 |
|---|---|---|
| 頁面算圖顯示 | 低 | Ghostscript 已有，但每次呼叫外部行程約 200ms＋，互動式重繪太慢，可能得改內嵌 pdfium |
| Canvas 編輯器（前端） | 中 | 選取、拖曳、縮放控制點、圖層順序、復原重做。估 800–1200 行 TS |
| 座標映射 | 中 | 螢幕像素 ↔ PDF 點，還要處理 `/Rotate`、`/CropBox`、以及 MediaBox 原點不在 (0,0) 的檔案。細節多且容易出錯 |
| 內容串流生成 | 低 | `images.rs` 已經做過 `cm … Do` |
| 圖片嵌入 | 低 | 已經會了 |
| 手繪與形狀 | 低 | 內容串流會生成之後就很簡單 |
| **字型內嵌與子集化** | **高** | **中文的真正瓶頸，見下節** |

## 四、字型那一關

中文字要內嵌到 PDF，需要：

- Type0 複合字型 ＋ CIDFontType2 後代字型
- CIDToGIDMap
- ToUnicode CMap（少了它，從 PDF 複製文字出來會是亂碼）
- **子集化**——不子集化的話，內嵌一份標楷體等於每個檔案多背 15 MB

子集化要解析 TTF 的 glyf / loca / cmap / hmtx 表再重建。聽起來很可怕，但**有現成的 crate**：
`subsetter`（Typst 專案，MIT/Apache-2.0）就是專門做這件事的，而且是 Typst 正式產品在用的。
這把風險從「好幾個月」壓到 **1–2 週**。

### 關鍵論點：字型工作一次解鎖三個工具

浮水印、加頁碼、以及編輯功能裡的文字，**全部卡在同一件事**。
所以字型內嵌不該記在「編輯 PDF」的帳上，它是共用基礎建設。

## 五、最強的反對理由：它跟現有架構根本不是同一種東西

目前 11 個工具全部是同一個模式：

```
N 個檔案 → 設定參數 → 執行 → N 個結果 → 存檔
```

編輯是：

```
1 個檔案 → 進入互動編輯階段（可能數十分鐘）→ 存檔
```

這會同時打破三件事：批次處理、拖放多檔的 UI，以及——最麻煩的——**暫存即刪的隱私模型**。

目前暫存檔的壽命是幾秒鐘。編輯階段是幾十分鐘。編輯到一半、還沒存檔的狀態要放哪裡？

- 放記憶體：大檔案吃不消
- 落地：那就是一個長時間存在的暫存檔，跟產品的核心承諾直接衝突

這不是實作細節，是**產品定位層級的衝突**。要做編輯，就得先想清楚怎麼跟「不留痕跡」共存。

## 六、建議：拆成三段，第三段可以不做

| 階段 | 內容 | 估時 | 用既有架構？ |
|---|---|---|---|
| **一** | 字型內嵌＋子集化基礎建設 → 直接產出**浮水印**與**加頁碼** | 1–2 週 | ✅ |
| **二** | **圖章**——在指定位置蓋上圖片（簽名檔、公司章） | 3–5 天 | ✅ |
| **三** | 互動式註記編輯器 | 3–4 週 | ❌ 需要新的 UI 範式與暫存模型 |

階段一與二完全沿用現有的批次模式，不需要互動編輯器，而且**已經涵蓋了「編輯 PDF」實際
使用情境的大部分**——絕大多數人開這個工具就是為了蓋個章、加個浮水印、標個頁碼。

階段三才是真正昂貴的那塊。等到有人真的開口要求再說。

## 七、如果最後還是要做階段三

兩個前提要先解決：

1. **算圖效能**——Ghostscript 每頁一次外部呼叫在互動場景下不可行，得評估內嵌 pdfium（BSD-3，授權相容）
2. **編輯階段的暫存策略**——建議：整份文件保留在記憶體，只在超過門檻時才落地，且落地檔一樣受
   `Ephemeral` 管理；另外要處理「編輯中當機」的情境，目前的啟動掃除會直接清掉未存檔的工作

而且要誠實命名。叫它「**註記**」而不是「編輯」，把「改不了原有文字」寫在界面上，
不要讓使用者帶著錯的期待進來。

# 八、v0.1 基準 續評估：兩個前提的實測結果

第七節列出階段三的兩個前提：算圖效能，以及編輯階段的暫存策略。
另外還有一個當時沒想到的問題——**編輯器本身要不要自己寫**。三個都量過了。

## 8.1 算圖效能：Ghostscript 不行，差 12 倍

同一份圖文混排 PDF，每頁一次獨立呼叫（模擬編輯器換頁）：

| 引擎 | 每頁耗時 |
|---|---|
| Ghostscript（現用） | **497 ms**（最快 418、最慢 534） |
| MuPDF WASM | **42 ms** |

按一下等半秒，使用者會覺得程式壞了。**Ghostscript 這條路在互動場景是死的**，
這點原本只是推測，現在是量出來的。

（附帶一提：MuPDF 開啟 100 頁 PDF 只要 9 ms。Ghostscript 光是行程啟動就不只這個數字。）

## 8.2 編輯器不必自己寫——但現成的那個對中文是壞的

PDF.js 從 3.x 起內建 `AnnotationEditorLayer`，支援 FreeText / Ink / Stamp / Highlight，
產出的是**標準 PDF 註記物件而非點陣圖**，還能 `saveDocument()` 直接寫回。Apache-2.0，
授權相容。看起來可以省下兩三週。

**但是它的中文是壞的。**

[mozilla/pdf.js#20117](https://github.com/mozilla/pdf.js/issues/20117)（2025-07-24 開啟，至今無維護者回應）：
含 CJK 字元的 FreeText 註記**不會產生 Appearance Stream（/AP）**，且 `/Contents` 的編碼有問題。
結果是這些註記在 Firefox 裡看得到，在 **Chrome、Edge 等 PDFium 基底的閱讀器裡完全消失**。
相關的 [#15769「Add non-Latin text annotations」](https://github.com/mozilla/pdf.js/issues/15769) 也還開著。

對一個繁體中文為主的產品，這是**否決條件**，不是可以繞過的小瑕疵。

## 8.3 MuPDF.js：實測全部通過

Artifex 官方的 WebAssembly 版本，npm 套件內含 WASM 二進位，不需要額外建置步驟。
**AGPL 授權——本專案本來就是 AGPL，相容。**

| 項目 | 實測 |
|---|---|
| WASM 體積 | 9.93 MB（brotli 壓縮後 **3.44 MB**） |
| 套件總大小 | 13.6 MB |
| 開啟 100 頁 PDF | **9 ms** |
| 算圖 @1.5x | **42 ms/頁** |
| 結構化文字 | **含字級**（實測標題 16pt、內文 10pt 正確分辨） |
| 中文 FreeText 註記 | **寫入成功、讀回正確** |

### 中文註記的關鍵驗證

pdf.js 的問題是「缺 /AP 所以別的閱讀器看不見」，所以光看它自己畫出來不算數。
我把 MuPDF 寫出的中文註記**丟給 Ghostscript（完全獨立的算圖器）算圖**——
紅色的「中文註記測試 ABC 123」清楚顯示在頁面上。MuPDF 產生了正確的 Appearance Stream
並內嵌了中文字型。

這正是 pdf.js 做不到的那一步。

### 順帶解決的兩件事

- **Markdown 的標題層級**：目前主程式用 Ghostscript 的 `txtwrite`，拿不到字級，
  標題只能靠版面猜（見 `docs/pdf-to-office.md`）。MuPDF 的結構化文字直接給字級，
  這個限制可以拿掉。
- **真塗黑（Redact）**：MuPDF.js 有 `applyRedaction()`，是真的從內容串流移除，
  不是畫黑框。這原本在「困難」清單上。

## 8.4 為什麼不用 mupdf-rs（原生 Rust 綁定）

`mupdf` crate 0.8.0（AGPL）會綑綁 MuPDF 的 C 原始碼，需要 C/C++ 工具鏈與 libclang。
社群回報 **Windows/MSVC 建置不穩定**（「有時候就是編不過」）。

用 WASM 版可以完全避開這些：npm 裝下來就有二進位，沒有編譯步驟，之後移植 Android 也一樣。

代價是**檔案內容會進到 WebView 的記憶體**，而不是像現在所有工具那樣只留在 Rust 這側。
評估下來這個差異可以接受：WebView2 是本機行程，我們不做任何網路請求所以不會產生快取，
而行程記憶體被作業系統換頁到磁碟這件事對 Rust 行程一樣成立。

但這代表**編輯器的資料路徑與其他 14 個工具不同**，要在程式碼與文件裡標清楚。

## 8.5 一個必須處理的隱私陷阱：增量儲存

PDF 的 incremental update 是把新物件**附加在原始檔案後面**，原始位元組完整保留。
pdf.js 與 MuPDF 的預設儲存行為都是這樣。

對「疊加註記」而言這是優點——原內容一個位元組都不動，正好符合本專案的原則。

**但如果使用者是想遮蔽敏感內容，這就是災難**：拿白色方塊蓋住身分證字號再存檔，
原本的文字**仍然完整躺在檔案裡**，用文字抽取工具一撈就出來。

所以：

- 一般註記 → 增量儲存，保留原內容（正確）
- **任何帶有「遮蔽」意圖的操作 → 必須用 `applyRedaction()` 並且完整重寫檔案，不能增量儲存**
- 界面上要把兩者分開，不能讓使用者以為畫個黑框就安全了

這條規則要寫進程式碼註解，不能只寫在文件裡。

| 階段 | 內容 | 估時 | 相依 |
|---|---|---|---|

| **二** | **圖章**（蓋簽名檔、公司章） | 3–5 天 | 無，`font.rs` 與 `annotate.rs` 已齊備 |
| **二之二** | 用 MuPDF.js 改善 Markdown 的標題層級 | 2–3 天 | MuPDF.js（小範圍試水溫） |

MuPDF.js 都給了。剩下的主要是編輯器 UI 與座標映射——那部分沒有變簡單。

**建議順序：二 → 二之二 → 三。** 階段二之二 是刻意安排的：用一個小範圍、低風險的功能

# 九、階段二與二之二的實作紀錄

## 9.1 階段二（圖章）：真正的工作是透明度

圖章本身很單純，難的是**簽名檔與公司章幾乎都是帶透明背景的 PNG**。原本的影像嵌入
只做 JPEG 原樣傳遞，沒有 alpha 通道——蓋出來會是一個白方塊糊住文件。

PNG 必須解碼後以 Flate 重新編碼，透明度則是獨立的灰階影像掛在 `/SMask` 上。
做完之後「JPG 轉 PDF」自動獲得 PNG 支援，改名為「圖片轉 PDF」。

`annotate.rs` 的疊加函式一般化成可以掛任意資源（字型或影像），浮水印、頁碼、圖章
共用同一條路徑。

## 9.2 階段二之二（MuPDF 整合）：踩到的坑與結果

**WASM 定位問題。** MuPDF 用 `new URL("mupdf-wasm.wasm", import.meta.url)` 找自己的
WASM 二進位。讓 Vite 打包 `mupdf.js` 之後，模組會變成 `/assets/index-xxxx.js`，
WASM 就會被找到 `/assets/mupdf-wasm.wasm`——那裡沒有東西。

解法是**完全不讓 Vite 碰它**：把三個檔案複製到 `public/mupdf/`，用變數當 specifier
做動態 import（變數可以讓 TypeScript 與 Vite 都不去解析這個路徑）。
模組 URL 固定是 `/mupdf/mupdf.js`，WASM 就穩定解析到 `/mupdf/mupdf-wasm.wasm`。

**資料路徑的改變。** Markdown 現在是唯一把檔案內容讀進 WebView 的工具。新增的
`read_file_bytes` 命令回傳 `tauri::ipc::Response` 而不是 `Vec<u8>`——後者會被序列化成
JSON 數字陣列，一份 30 MB 的 PDF 會膨脹成上百 MB 的字串。

**備援路徑。** MuPDF 載入失敗時自動退回 Ghostscript 抽文字。多一條路徑是額外的維護
成本，但這是新引擎第一次進到產品裡，值得留退路。

**成果。** 標題層級不再靠行寬猜，直接來自字級；段落邊界也直接用 MuPDF 的區塊，
比從行寬推斷可靠得多。
